# Module 9-04: Communication Skills

> Master the day-to-day communication patterns that build client confidence.

## Overview

Every interaction with a client either builds or erodes trust. This module covers communication patterns that project competence, professionalism, and partnership.

> **Generic Foundation:** Planned: General Communication Guide — this module adds CF-specific terminology and client scenarios.

## Learning Objectives

By the end of this module, you will be able to:

- [ ] Use confident language instead of hedging
- [ ] Ask clarifying questions effectively
- [ ] Communicate technical risk without causing alarm
- [ ] Handle difficult conversations professionally
- [ ] Write clear client-facing emails
- [ ] Set and manage expectations
- [ ] Know what NOT to say to clients

## Confident Communication Patterns

### Replace Weak Phrases

| Instead of... | Say... |
|--------------|--------|
| "I think..." | "Based on the assessment..." |
| "Maybe..." | "One approach would be..." |
| "I don't know..." | "I'll verify that and follow up with a recommendation." |
| "We could try..." | "I recommend we..." |
| "No, that won't work..." | "There are some considerations with that approach..." |
| "That's impossible..." | "That would be challenging because... Let me suggest alternatives." |
| "We never did that..." | "We've found different approaches work better, but we can validate for your case." |

### Use Confidence Builders

- "Based on what you've described..."
- "Our experience shows..."
- "The recommendation would be..."
- "There are a couple of approaches..."
- "The main challenge with that is..."
- "What we've seen work well is..."

## CF-Specific Language Guide

### For Non-Technical Clients

| Technical Term | Client-Friendly Term |
|---------------|---------------------|
| ColdFusion | "Your application platform" or "your web server" |
| CFML | (Avoid entirely — say "your existing code") |
| JVM | "The underlying engine" or "server infrastructure" |
| Database | "Your data storage" or "your records" |
| API | "Integration points" or "connections to other systems" |
| Framework | "The structure of your application" |
| Refactoring | "Restructuring" or "modernizing" |
| Technical debt | "Accumulated complexity" or "maintenance overhead" |

### For Technical Clients

You can use full technical terminology but still communicate clearly:

> "The main risk is CF2018 reaching end-of-life in December. We'd need to either upgrade to CF2023 or migrate to Lucee. Both have migration paths, but Lucee eliminates the licensing cost."

## What Never to Say

### About Code/Architecture

| Never Say... | Because... |
|-------------|-----------|
| "Your code is terrible." | Destroys trust, unprofessional |
| "This framework is bad." | Opinion, not professional |
| "This needs a complete rewrite." | Destroys confidence, rarely true |
| "We always do it this way." | Inflexible, close-minded |
| "That's not how we do things." | Dismissive |

### About Uncertainty

| Never Say... | Because... |
|-------------|-----------|
| "I don't know." | Too vague, shows no initiative |
| "We don't know." | Unprofessional for an expert |
| "That's impossible." | Rarely true |
| "It'll be easy." | Sets wrong expectations |
| "It'll take only two days." | Almost always wrong |

### About Problems

| Never Say... | Because... |
|-------------|-----------|
| "That wasn't my fault." | Blame-shifting |
| "The previous developer..." | Blaming others |
| "We didn't know..." | Shows lack of process |
| "That's not in scope." | Dismissive without context |

## What to Say Instead

| Situation | Response |
|----------|----------|
| Unknown technology | "I haven't worked with [X] specifically, but my approach would be to research it and come back with recommendations." |
| Challenge identified | "We've identified a consideration that affects our approach. Here's what I'd recommend..." |
| Scope creep | "That's an interesting idea. Let's note it for phase 2 so we stay on track for today's goals." |
| Mistake made | "We've encountered an issue. Here's what happened and what we're doing to resolve it." |
| Over budget/time | "We're tracking [X]% over on [item]. We have options: adjust scope, add resources, or extend timeline. Which works best for you?" |

## Email Communication

### Structure for Status Updates

```
Subject: [Project Name] Status Update - [Date]

Hi [Name],

Here's the status update for this week:

✓ Completed
- [Item 1]
- [Item 2]

→ In Progress
- [Item 1] - [X]% complete, expected completion [date]
- [Item 2] - On track

⚠️ Blockers/Considerations
- [Issue] - [Impact] - [Proposed resolution]

📅 Next Week
- [Planned work]

Let me know if you have questions or want to discuss any items.

Best,
[Name]
```

### Structure for Technical Explanations

```
Subject: [Topic] - Technical Explanation

Hi [Name],

You asked about [topic]. Here's a plain-language explanation:

What it is:
[Brief, non-technical description]

Why it matters:
[Business impact in their terms]

What we recommend:
[Clear recommendation]

What this means for your project:
[Specific impact on timeline/cost/etc.]

Let me know if you'd like to discuss further.

Best,
[Name]
```

## Meeting Communication

### Before Meetings

- Review the agenda
- Prepare answers for anticipated questions
- Identify your key message (one sentence)
- Have backup information ready

### During Meetings

**DO:**
- Listen more than speak
- Take notes
- Ask clarifying questions
- Summarize to confirm understanding
- Pause before answering difficult questions

**DON'T:**
- Interrupt
- Argue
- Go off-topic
- Dismiss concerns
- Speak without purpose

### After Meetings

- Send summary within 24 hours
- Document action items
- Follow up on commitments
