# 09. Code Review

**Status:** Draft · **Owner:** CoE Team · **Last updated:** 2026-11-06 · **Next review:** 2027-02-06

Code review catches defects, spreads knowledge and keeps a codebase consistent. A good review checks the things that
matter, objectively and kindly. Back to the [roadmap](./README.md).

## What to review

Spend review time on what tools cannot check. Leave formatting to the formatter.

**What to learn:**

- Reviewing intent, correctness, readability, design, tests and security
- Leaving indentation, quotes and line length to the formatter and linter
- Reading the PR description and tests first, so you know what the change is meant to do

**Resources:**

- [Google's code review guide](https://google.github.io/eng-practices/review/reviewer/), on what to look for

**Level:** Practitioner · Core

## Giving feedback

The way you write a comment decides whether it helps. Objective, specific comments get fixed; vague or personal
ones start arguments.

**What to learn:**

- Objective comments that can be checked against the code, instead of "I would have done it differently"
- Asking questions that invite the author to think: "Could this be a separate function?"
- Labelling each comment: must fix (a defect), should consider (an improvement) or nit (a minor preference)
- Saying what is good, too

**Resources:**

- [How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html), Google

**Level:** Practitioner · Core

## The review checklist

A shared checklist means every reviewer checks the same things, whoever they are. Run it on every PR you review.

**What to learn:**

- **Readability:** can someone new understand it without asking?
- **Maintainability:** will the next person to change it find it easy?
- **Design:** does each part have one responsibility, with dependencies passed in?
- **Error handling:** does it fail fast and log useful context, with no secrets in logs?
- **Security:** are inputs validated, queries parameterized and permissions checked on the server?
- **Tests:** is the new behaviour tested at the right level?
- **Performance:** was any performance claim measured?
- **Documentation:** do the docs match any change to a public API?
- **AI disclosure:** if AI helped, is it disclosed in the commits?

**Resources:**

- [Security Audit Checklist](../../security/audit/security-audit-checklist.md), Techversant
- Stack checklists that add to this one:
  [Node.js and TypeScript](../../standards/nodejs/nodejs-typescript-code-review-checklist.md) and [ColdFusion](../../standards/coldfusion/coldfusion-code-review-checklist.md)

**Level:** Practitioner · Core

## Self-review

Review your own PR before anyone else does. You will catch the obvious problems and save your reviewer's time.

**What to learn:**

- Reading your own diff in the PR view, as a reviewer would
- Running the review checklist on your own change
- Adding notes to the PR where a reviewer might be confused

**Resources:**

- [The review checklist](#the-review-checklist), on this page

**Level:** Foundation · Core

## Reviewing AI-generated code

AI-generated code needs the same review as any other code, plus a few extra checks for its typical mistakes.

**What to learn:**

- Checking that functions and libraries the code uses really exist
- Looking for missing edge cases, insecure defaults and code that does more than was asked
- Making sure no Red Zone code was generated by AI

**Resources:**

- [AI code review checklist](../../standards/general/ai-era-coding-guidelines.md#appendix-ai-code-review-checklist-),
  in the Techversant AI Era Coding Guidelines

**Level:** Practitioner · Core

## Project: Review Three Pull Requests

**Brief:** Review three pull requests from other engineers on this roadmap, or real PRs on your project agreed with
your lead. Get your own bookmarks PR reviewed with the same checklist, and respond to every comment.

**Size:** 2 days, spread across a week

**Verification**, checked by a reviewer:

- [ ] Before requesting review of your own PR, you ran the checklist on it and fixed what you found
- [ ] Each of your three reviews covers every item in the review checklist
- [ ] Every comment you wrote that asks for a change is labelled must fix, should consider or nit
- [ ] Each review includes at least one question rather than an instruction, and at least one specific piece of
  praise
- [ ] At least one of the PRs you reviewed included AI-generated code, and your review checks it against the AI code
  review checklist
- [ ] The three authors confirm your comments were clear and fair
- [ ] Every comment on your own PR is resolved with a change or a reply
